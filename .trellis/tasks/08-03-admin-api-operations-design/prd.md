# 设计 Admin 菜单与 API 运营数据管理

## 目标

重新设计 `apps/admin` 的后台菜单和 `apps/api` 的管理能力，让管理员可以查看 Web 端各业务模块的运行情况，查询用户与朋友配置，追踪 AI 调用的流量和 Token 消耗，并为后续按用户、模型、业务场景和时间汇总统计保留结构化调用数据。

本次先完成需求与技术方案。实现阶段保留 `apps/web` 的现有 UI 架构，只补充按朋友发起单聊和发送消息所需的入口、状态与 API 接入。

## 背景

- 当前 Web 原型覆盖聊天、通讯录和设置，正式 Web 代码是在已有 API 能力上重构 UI。
- Admin 菜单中的“数据概览”没有实际数据接口，“情绪记录”全部使用静态示例数据，两者不能反映当前产品能力。
- Admin 已有可用模块包括用户管理、角色权限、默认头像和模型配置。
- API 已有用户、朋友、单聊、群聊、记忆、主动关怀、消息反馈和 LLM 配置模块。
- 单聊消息、群聊消息、朋友配置、记忆、主动关怀和消息反馈已经写入 D1，可以作为业务事实来源。
- 当前单聊 API 仍使用每个用户唯一一条的 `companion_conversations`，请求和消息没有 `agentId`；`agent_conversations` 只有会话统计，没有对应的单聊消息表。
- Web 已按朋友呈现多个单聊，但 API 尚不能保存每个朋友各自的单聊历史，也不能把单聊 Token 归到具体朋友。
- Web 朋友档案已有“开始聊天”按钮，但目前只跳到 `/chats`；聊天头像菜单已有“发起私聊暂未开放”；`/chats/direct/:id` 路由可以复用。
- AI runtime 已统一返回 `promptTokens`、`completionTokens` 和 `totalTokens`，但业务调用目前没有把 usage 持久化，也没有统一记录调用场景、模型、耗时、状态和错误。
- API 目前没有管理员查询聊天运营数据、朋友配置或 LLM 调用记录的接口。
- 项目仍处于开发阶段，现有 companion、会话、消息、记忆和反馈数据不要求保留。

## 需求

### R1. 后台菜单

- 删除没有真实业务来源的“情绪记录”菜单。
- 用能对应 Web 业务和 API 数据的菜单替换当前占位结构。
- 区分运营查看、AI 运行管理和系统管理，避免所有菜单平铺在同一级。
- 每个菜单都要明确数据来源、主要列表字段、筛选条件、详情内容和允许执行的操作。
- 后台增加“朋友管理”菜单，不使用“用户朋友”名称。
- 后台增加“消息反馈”菜单，只处理用户主动提交的反馈与关联消息。
- Token 用量不单独设置一级菜单，统一从“用户管理”进入查看。
- 删除没有真实配置来源的“系统设置”占位菜单；默认头像、模型配置和角色权限保留为独立模块。

### R2. 用户管理视角

- 用户列表除账号状态外，应能查看注册时间、最近登录、最近活跃、消息数、朋友数和群聊数。
- 用户详情应集中展示账号信息、使用摘要、朋友、会话和 AI 调用记录，避免管理员在多个菜单中重复搜索同一用户。
- 管理员只能通过 Admin 专用接口读取这些数据，不能复用 Web 用户接口返回后台字段。
- 用户详情不提供全量聊天原文，只展示会话数量、消息数量、最近活跃时间、AI 用量和运行状态等元数据。
- 用户列表提供 Token 用量操作按钮，点击后打开当前用户的用量抽屉。
- 用量抽屉顶部展示累计输入、输出、总 Token，今日输入、输出、总 Token，累计调用次数、今日调用次数、失败调用次数和最近调用时间。
- 用量抽屉按用量主体列出累计与今日用量。每行展示主体名称、主体类型、朋友来源、累计输入、输出、总 Token、累计调用次数、今日输入、输出、总 Token、今日调用次数和最近调用时间。
- 用量抽屉中的“朋友”指该用户实际聊天使用的 Agent，不与后台权限角色混用。
- 用量主体分为具体朋友和“系统流程”。系统流程汇总意图识别、情绪分析、发言选择、回复质检等无法关联具体朋友的调用。
- 用户总量必须等于所有朋友用量与系统流程用量之和，不把系统流程 Token 平均分摊给朋友。
- 用量抽屉支持进入调用明细，按时间、朋友、业务场景、模型和状态筛选。
- 调用明细展示发生时间、业务场景、用量主体、会话类型、会话标识、Provider、模型、输入 Token、输出 Token、总 Token、耗时、状态、错误分类和请求关联标识。
- 调用明细不保存或展示原始 Prompt、模型回复和聊天原文。
- “今日”统一按 `Asia/Shanghai` 的自然日计算，接口返回统计区间的开始与结束时间。

### R3. 朋友管理

- 朋友管理同时展示系统内置朋友和用户自建朋友，并提供“全部 / 系统 / 用户”来源筛选。
- 系统内置朋友与用户自建朋友必须有明确、可查询的来源字段，不能通过名称或所属用户是否为空临时推断。
- 列表至少展示名称、来源、所属用户、状态、创建时间、更新时间、会话数、消息数和最近使用时间。
- 详情应展示朋友的基础资料、人设、语气、边界、默认 prompt、记忆数量和参与的群聊。
- 用户自建朋友默认只读，避免管理员绕过用户修改私人配置。
- 系统内置朋友使用全局共享定义，不复制到每个用户名下。
- 用户与系统朋友建立各自独立的会话和记忆；聊天、记忆和 Token 用量归对应用户。
- 用户不能修改系统朋友的人设、语气、边界和 Prompt。
- Admin 可以创建、编辑和停用系统朋友；配置更新只影响后续 AI 调用。
- 已被用户使用的系统朋友不能直接删除，只能停用；历史会话和统计继续关联原朋友记录。
- 用户自建朋友由所属用户维护，Admin 第一版只读。
- 系统朋友和用户自建朋友必须使用同一套可被会话、记忆、群聊成员和 AI 调用记录引用的 Agent 标识。

### R4. AI 调用记录

- 每次模型调用应生成一条独立记录，不只记录一轮聊天的最终结果。
- 记录至少包含用户、业务场景、会话或群聊关联、朋友关联、模型配置、Provider、模型名称、输入 Token、输出 Token、总 Token、耗时、调用状态、错误分类和发生时间。
- 单聊流式生成、群聊意图判断、情绪分析、发言选择、Agent 回复、回复质检、跨 Agent 回复计划和主动关怀等调用应使用可筛选的场景标识。
- Token usage 缺失时仍保存调用记录，并明确标记 usage 不可用，不能按 `0` 处理。
- AI 调用明细从用户管理的 Token 用量抽屉进入，支持按时间、朋友、业务场景、模型和状态查询。
- 第一版只统计 Token，不计算或展示费用。
- 第一版不设置自动过期时间；调用明细持续保留，累计 Token 直接从完整明细汇总。

### R5. 管理员敏感访问审计

- 管理员查看消息反馈中的关联消息时，应写入管理员审计记录，包含管理员、反馈、查看时间和请求关联标识。
- 管理员审计记录不保存聊天原文，只保存谁在什么时候查看了哪条反馈。
- 第一版不设置管理员审计记录的自动过期时间。

### R6. 数据概览

- 数据概览必须从真实 API 汇总数据读取，不保留欢迎页式占位内容。
- 第一版至少展示用户、新增用户、活跃用户、消息量、AI 调用量、Token 消耗、失败率、朋友数和群聊数。
- 每个指标都要写明统计口径、时间范围和数据来源。
- 第一版允许按查询实时聚合；只有实际出现查询性能问题时再增加按日汇总表或定时任务。
- 清理历史 AI 调用明细前必须先建设按日汇总，保证累计 Token 不因明细删除而减少。

### R7. 按朋友区分的单聊

- 单聊请求、会话、消息和 AI 调用必须关联具体朋友，才能生成正确的朋友用量统计。
- 每个用户与同一个朋友最多有一个单聊会话；不同用户使用同一个系统朋友时，会话和消息相互隔离。
- 不迁移现有每用户唯一的 companion 数据。开发数据库直接删除旧 companion 会话、消息、记忆、反馈和关怀数据，再创建按朋友区分的新结构。
- Web 必须补充发起单聊功能，系统朋友和当前用户自建的活跃朋友都可以发起单聊。
- 发起单聊操作应幂等：已有会话时直接打开，没有会话时创建后打开，不能重复创建同一用户与朋友的会话。
- 发起单聊后进入现有 `/chats/direct/:id` 路由形态，消息列表和发送请求读取该朋友对应的会话。
- 朋友已停用或归档时不能新建单聊；历史会话仍可查看，但不能继续触发该朋友的 AI 回复。
- Web 的朋友列表、朋友详情和聊天区域应至少提供一个清晰的发起单聊入口，具体复用位置以现有组件为准。
- 朋友档案的“开始聊天”和聊天头像菜单的“发起私聊”应调用同一个幂等发起单聊动作。
- 发起过程中按钮显示请求状态；失败时留在当前页面并显示具体错误，成功后跳转到对应单聊。

### R8. 主动关怀

- 每个用户保留一份主动关怀设置，并指定一位活跃朋友作为关怀发送者。
- 关怀朋友可以是活跃系统朋友或当前用户拥有的活跃用户朋友。
- 开启主动关怀前必须选择朋友；不允许多个朋友同时主动关怀。
- 关怀消息写入该朋友与用户的单聊会话，AI 调用和 Token 归该朋友。
- 关怀朋友被系统停用或由用户归档后，关怀计划停止执行，用户重新选择朋友后才能继续。
- Web 设置页复用现有主动关怀面板，只增加关怀朋友选择和不可用状态提示。

### R9. 数据边界

- D1 是业务记录和运营记录的唯一事实来源；Admin 只保存筛选、分页、弹窗和请求状态。
- Admin API 与 Web API 分开定义 route、contract 和 presenter，可以共用 service 或 repository 的底层读取能力。
- `packages/contracts` 只保存 Admin 请求 schema、响应 DTO 和错误码，不保存数据库 record 或页面 view model。
- Admin 默认不能浏览用户聊天原文。用户主动提交消息反馈后，反馈详情可以显示该条用户消息与对应 AI 回复，用于问题排查。
- 反馈详情不扩展为会话浏览入口，不返回同一会话中的其他消息。
- 本次不新增用户操作记录；新增用户、活跃用户、消息量、朋友数、群聊数和反馈量从现有业务表统计。

## 不在本次范围

- 重做 Web 端现有页面结构和视觉样式。
- 收集所有前端点击、曝光、停留时长等产品分析埋点。
- 用户登录、页面访问、配置修改和业务操作的统一事件日志。
- 提前建设独立数据仓库、BI 平台、消息队列或复杂定时任务系统。
- 自动计费、充值、套餐和账单结算。
- 模型价格、币种、价格生效时间和历史调用费用估算。
- 未经确认让管理员直接修改或删除用户聊天、记忆和朋友数据。
